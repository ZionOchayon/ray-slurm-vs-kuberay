# Build notes (observations, not results)

What actually happened while building, including surprises. Times are Israel time (+03:00). No number in this file is a benchmark.

## 2026-10-24 (v0.1)

- 14:29: Docker Desktop's UI was running, but the engine answered HTTP 500 and WSL was not installed, so the Linux engine VM had never started.
- 14:37: installed WSL 3.0.3 and the VirtualMachinePlatform feature with `wsl --install -d Ubuntu-24.04 --no-launch` (elevated). Windows needs a reboot before WSL works.
- Gotcha (from upstream `docker-entrypoint.sh` @3.0.2): compute containers rename themselves to `c1`/`c2` after start, and find their replica number by resolving `${COMPOSE_PROJECT_NAME}-cpu-worker-N`. So the compose project name must stay `slurm`, and `hostname --ip-address` for `c1` may not resolve. The sbatch falls back to `hostname -I` and prints `GOTCHA:` in the job log when it does.
- Gotcha: GNU make reports any failing recipe as exit 2, so `make up` cannot return the script's exit 1 or 124. The checks test for "non-zero" plus the message, not the exact code.
- Gotcha: GitHub Actions runs steps with `bash -e`, which ignores the status of `! cmd`. Negative CI checks use `if cmd; then exit 1; fi`.

## 2026-10-27 (v0.2)

Built in a cloud container (4 vCPU, 15 GiB, cgroup v1) and on GitHub-hosted runners. UTC times.

- CI on `main` had never reached the cluster: the "Hygiene: pins" step grepped `.github/workflows/*.yml` for `:latest`, and its own command line contains that pattern, so it always failed. The pattern is now `[:@]latest\b`, which matches the same text everywhere except itself. The first run with the fix passed the whole v0.1 job (5 m 39 s).
- Gotcha (CI, first v0.2 run): `make up` failed with `container slurm-cpu-worker-2 exited (1)`. Upstream's entrypoint (`set -e`) finds its replica number by resolving `slurm-cpu-worker-1`, `-2`, … in order and stops at the first name that does not resolve; if worker 1's DNS entry is not there yet, worker 2 falls back to `return 1` and exits. `slurm/worker-entrypoint.sh` now waits until every replica name resolves before running the upstream entrypoint.
- FR-12 HYPOTHESIS confirmed: Ray Train V2 resumes a run that already **finished**. `make train-slurm EPOCHS=3` on a finished 2-epoch run logged `restored epoch=1`, trained only epoch 2 and added `checkpoint_epoch_002`. The restore comes from `checkpoint_manager_snapshot.json` in the run directory. The `restored` line appears twice in the Slurm job log (the line is printed once by rank 0).
- `torch_num_threads` is 1 inside Ray Train workers (local runs and the local Slurm cluster), which settles the M2 UNVERIFIED item for this setup. It matches each worker's `num_cpus=1` (Ray sets `OMP_NUM_THREADS` from the CPUs an actor reserves).
- D1 kill-worker: the process to kill is `ray::RayTrainWorker` (`pkill -9 -f RayTrainWorker`). Surprise: killing it 0.5 s after `checkpoint_epoch_000/model.pt` appeared on disk restarted the worker group **from scratch** (no `restored` event; epoch 0 trained again). Ray Train V2 registers a checkpoint in the controller asynchronously after `report()`, and only registered checkpoints are restored. The drills now inject only after the checkpoint is listed in `checkpoint_manager_snapshot.json`.
- D2 preempt: both variants (USR1 trap → `scontrol requeue`, and `scontrol requeue` by an admin) kept the job ID and set `SLURM_RESTART_COUNT=1`; the run resumed from its latest checkpoint. The requeued job started again about 140 s after the requeue (sacct Submit 17:49:31, Start 17:51:51) on an otherwise idle cluster; that wait dominates D2's time to resume on Slurm. Its cause is UNVERIFIED (likely a begin-time delay Slurm applies to requeued jobs; check `scontrol show job` while it is pending).
- D3 surprise 1: upstream's `slurm.conf` has `SelectTypeParameters=CR_Core_Memory` and no `DefMemPerNode`/`DefMemPerCPU`, so a job without `--mem` is allocated **all** of each node's memory and a second job can never share the nodes, whatever its CPU request. Memory is not enforced (`ConstrainRAMSpace=no`). `make train-slurm` now passes `--mem=$(MEM_PER_NODE)` (default 2G) so the scheduler can pack jobs.
- D3 surprise 2, configuration (a): with nodes that fit two jobs, both `ray symmetric-run` jobs started their head on the same node and port 6379. **Neither** ran `train.py`, and Slurm recorded **both** as `COMPLETED 0:0` (both logs: `Failed to start Ray: ... ray start --head ... returned non-zero exit status 1`). The SPEC HYPOTHESIS (job 2 fails fast, job 1 unaffected) is refuted. Only `make verify`'s artifact checks caught it, which is risk R8 in practice. On the same host, (b) `--exclusive` ran the two jobs one after the other, and (c) `ray-manual.sbatch` with per-job port blocks and temp dirs ran both at the same time, and both passed `make verify` (one rep each).
- `ray start --ray-client-server-port` fails unless `ray[client]` is installed; the images install `ray[train]`, so Ray starts no client server and `ray-manual.sbatch` leaves that port of the block unused.
- Ray 2.59.0 turns on token authentication for `ray start --head` when `~/.ray/auth_token` exists, and a plain local `ray.init()` creates that file. Worker nodes started without the token then fail with `InvalidAuthToken`. The lab containers never create the file, so the Slurm launchers run without tokens; seen only when testing on a host that had run `ray.init()` before.
- `ray stop` is node-wide: it would also stop another job's Ray on a shared node, so `ray-manual.sbatch` ends only its own `srun` steps on exit. SIGTERM to `ray start --block` stops its raylet and GCS (checked: no Ray process left).
- kind does not run inside the cloud container used for development: Kubernetes 1.37's kubelet refuses cgroup v1 (`failCgroupV1`), and with that overridden locally, runc still cannot set `oom_score_adj` in the nested VM. The K8s side was therefore developed against CI's kind job only.
- K8s, first CI runs: (1) the runner ran out of disk while `kind load` copied the Ray image (several GB) into the node, a second copy next to Docker's; the kind job now deletes preinstalled toolchains first. (2) With CPU requests of 500m per Ray pod, the worker pod stayed Pending for 20 min on the 2-vCPU private runner: the control plane and operator request about 1 CPU, and KubeRay's default submitter pod requests 500m. The RayJob now gives the submitter 100m, and CI requests 200m per Ray pod (`K8S_CPU_REQUEST`); limits and `num-cpus` stay at 2, as SPEC FR-22 asks, and the default request outside CI stays 2. (3) With a 2Gi memory limit, Ray's memory monitor killed both Train workers when the head pod reached 1.90 of 2.00 GB (the head also runs the GCS, dashboard, driver and Train controller); the limit is now 4Gi.
- K8s, UNVERIFIED items settled on KubeRay 1.7.1 with Kubernetes 1.37 (kind v0.33.0): the operator works; RayJob has `spec.backoffLimit`; the default submission mode creates a submitter Job (`job/<rayjob>` ran `ray job submit`). A 2-epoch synthetic RayJob reached `SUCCEEDED` 57 s after `kubectl apply` in CI, and `make verify SCHED=k8s` passed C1–C6 with the same `train_py_sha256` as the Slurm runs (FR-21).
- Tear-down cost of `ray symmetric-run` (dev host, one 1-epoch job each, timestamps from slurmctld): `run_end` came 33 s after submission but the job ended at 104 s; the head's `ray stop` waited out its 16 s grace period ("Stopped only 4 out of 5 Ray processes"), then the worker node's raylet logged `Failed to connect to GCS within 60 seconds` before its `ray start --block` gave up. The same job through `ray-manual.sbatch` ended 2 s after `run_end`, because the script ends its own steps. This is why D3's makespan for (a) and (b) is about 2.7 times that of (c) on the bench runner, where all three ran one job after the other.
- Bench runner: GitHub's `ubuntu-24.04` private-repo runner has 2 vCPUs, so each Slurm node advertises 2 CPUs and each job takes both. In D3, (a), (b) and (c) therefore all ran one after the other there, and so did the two RayJobs in (k), whose second cluster waited for CPU; the co-scheduled outcomes for (a) and (c) above come from the 4-CPU development host.
- K8s D2 (full bench): `kubectl delete pod` on the head gives it the default 30 s termination grace period, and the Ray head kept training through it (with 4 epochs the run even finished inside it). The submitter Job then ran a second pod that resubmitted the entrypoint (`Found 2 pods` in its log), and the new driver resumed from the latest registered checkpoint. Whether that retry came from the submitter Job's own `backoffLimit` or from the RayJob's is UNVERIFIED; check `kubectl get rayjob -o yaml` (`status.failed`) during the drill. Before the worker pod had rejoined, Ray Train placed both workers on the new head (`SPREAD` is best effort), so C4 failed on those runs; D2 records this as `D2_workers_on_two_nodes` instead of failing on it.
